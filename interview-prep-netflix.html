Netflix ML Scientist — Interview Script

On-Device ASR & Quantization Deep Dive · ~15 min project portion

1. Opening Script ~90 sec

I spent three years leading on-device ASR at Amazon Alexa. The core challenge: Echo devices have constrained memory and compute, so cloud ASR doesn't work — you need models that run fast on neural network accelerators.

I led sub-8-bit quantization, compressing ASR models from 32-bit down to 5-bit. The naive approach — post-training quantization — blows up word error rate by over 10%, because 5-bit gives you only 32 weight values instead of 256.

I invented a training scheme based on Lloyd-Max theory that learns optimal quantization centroids during training, and co-designed the runtime with the hardware team. Result: 30% latency reduction, 30% model size reduction, zero accuracy loss. Deployed to all Echo and Echo Dot products globally. Published at Interspeech.

I then generalized the method into a plug-and-play solution called General Quantizer, which works on any architecture — RNN-T or Conformer, on-device or cloud. Published at SLT, plus a patent.

Pause here. Let them ask. Being concise signals seniority.

2. Q&A Bank ~13 min

Why 5-bit specifically, not 4 or 6?
5-bit is the sweet spot. Compared to 8-bit, it already brings down the bandwidth by over 37%. We tested 4-bit — it works on RNN-T with less than 3% degradation, but attention layers in Conformer degrade noticeably at 4-bit. 5-bit is where we got zero accuracy loss across all architectures — RNN-T and Conformer alike. And importantly, we were able to get impressive accuracy on par with the 32-bit baseline, which gave us the confidence to get buy-in from the engineering team to invest their engineers in co-designing the runtime.
Why not just use post-training quantization?
First, speech and audio models are more sensitive to quantization noise than LLMs. The model size is much smaller — well under a billion parameters — so there's less redundancy to absorb the precision loss. We tried post-training quantization to 8-bit and it blew up the accuracy by over 10%. The hardware only supports INT8, not FP8 — the range is fixed — so it was a clear no-go. We had to do quantization-aware training. Now, these days there are advanced approaches like SmoothQuant and activation-aware weight quantization, but for speech models, I still believe QAT is the safest approach. Also the model is small enough that training won't take more than three weeks. Our recipe is stable — you don't need extensive ablation — so financially and accuracy-wise, it's the best shot. I proved this in production: when I brought GQ to cloud Conformer, the existing post-training approach had a silent quantization-induced loss nobody had challenged. GQ recovered 1–3% WERR on tail queries.
Walk me through how the algorithm works.
Three layers. First, you run the Lloyd-Max algorithm — essentially K-means clustering — on a trained model, per kernel. You get a set of 32 centroids per kernel. That's your prior knowledge to initialize quantization-aware training. Second, a soft compressor — a regularizer added to the loss function — that nudges weights towards those predefined centroids from K-means. Third, a hard compressor that periodically snaps every weight to its exact nearest centroid to ensure convergence. That way you don't need a very large blending weight that would dampen the main training objective. Soft gets you close, hard locks it in. Together, they eliminate the gap between training and runtime.
What's GQ and why did you build it?
Our previous sub-8-bit quantization requires running K-means clustering on a trained model to extract reference centroids per layer. That's overhead — you need a ground truth. And when it comes to Conformer instead of RNN-T, there are hundreds of kernels because of the CNN components. Too many nitty-gritty details to calibrate each kernel. That's the motivation for GQ: why don't we make the centroid set learnable? We completely get rid of all regularizers. It's self-adjustable centroids through Softmax annealing in mu-Law space. It's just a callback — plug-and-play. Same compression wins, works on any architecture, and the code is reduced by 30%.
How did you handle hardware co-design?
I sent feature request tickets to the hardware team from day one so we could validate the hypothesis early. They built a K-means runtime quantization that matches our in-training Lloyd-Max centroids. Parallel workstreams — I owned the training side, they owned the SDK. The 5-bit prototype on NNA showed 17% faster frame processing than 8-bit, which gave us the green light. That coordination was honestly harder than the algorithm itself.
Which teams did you collaborate with?
Three main groups: the modeling team who owns the acoustic model and rescorer, the hardware team who builds the neural network accelerator SDK, and the runtime team who owns inference execution. My role sat at the intersection — I co-designed the training-side quantization with the hardware team's runtime quantization so they matched. I also onboarded other scientists to productize 5-bit quantization across multiple locales, created runbooks and tutorials.
Why does 5-bit sometimes beat the 32-bit baseline in accuracy?
It's not luck — it's consistent across test sets. The quantization acts as a regularizer that stabilizes training. With our soft-to-hard Softmax annealing, weights are guaranteed to stay within a negative-1 to positive-1 interval — no outliers that you'd otherwise see. Constraining weights to 32 centroids reduces the search space, making it an arguably easier optimization. Conformer at 5-bit: 5.50 WER vs 5.74 for 32-bit on test-clean. But if you really want guaranteed accuracy gains, here's the production insight: with 5-bit quantization, you break down latency by 30%. That's huge headroom. You can make the model slightly larger — stack one extra encoding layer — and that extra layer greatly helps WER, especially on critical production test suites. Bigger model, still faster. That's the real win.
What would you do differently?
I'd start with GQ's simpler approach from the beginning. S8BQAT's regularizer was effective but over-engineered in hindsight. The Softmax annealing in GQ is more principled, easier to tune, and works across architectures without manual centroid configuration. That said, S8BQAT taught me what mattered, which is why GQ is so clean.
How does this apply to Netflix games?
Latency is always the key for real-time services. For Netflix games, I'd assume it's real-time voice interaction: ASR to transcribe player commands, TTS to synthesize NPC dialogue in high fidelity, voice cloning for personalization. Latency plays a central role in all those components, and the hardware is always with limited bandwidth, compute, and memory. It's the same problem I solved — you want to compress the model without losing quality. You're trying to win the trade-off game. Also, the plug-and-play nature of GQ means the solution is model and platform agnostic. At Netflix, things change fast — you upgrade model architectures, cover more device types, offer multi-tier quality bars. A plug-and-play solution lowers the friction for the research and development teams.
How does quantization relate to LoRA/PEFT?
They're complementary. With LoRA, you can recover quantization-induced loss. You could quantize your model to 4-bit or even lower if that brings actual latency benefit, then attach low-rank adapters trained on a small calibration dataset for maybe half a day or less. You preserve 98% of performance and your base weights are at even lower bit depth. Both are about parameter efficiency — same philosophy. You don't need full precision or full rank to preserve model capacity. For Netflix, for the best latency win, you'll need both: quantize the base weights, then run LoRA for fine-tuning TTS voices, personalized adaptation, or to recover any accuracy gap induced by quantization.

6. Coding — Sliding Window Template

Your weakness: manual right += 1 inside if/else causes off-by-one bugs. Never do that again. Use this pattern:

# The template: add, shrink, measure. That's it.
def solution(chunks, B):
    left = 0
    curr_sum = 0
    curr_max = 0

    for right in range(len(chunks)):   # right ALWAYS advances
        curr_sum += chunks[right]       # 1. ADD
        while curr_sum > B:             # 2. SHRINK if needed
            curr_sum -= chunks[left]    #    subtract FIRST
            left += 1                   #    then move
        curr_max = max(curr_max, right - left + 1)  # 3. MEASURE

    return curr_max

Why this kills your old bugs

Old BugWhy It's Gone
chunks[0] never addedfor right starts at 0, add before anything else
Subtract wrong elementSubtract first, then move left — correct order
right - left off by oneright - left + 1 — both inclusive
right < len - 1 misses lastfor right in range(len) — visits every element

How to narrate (talk to the interviewer, not yourself)

Before coding: "This is a sliding window problem. All chunk sizes are positive, so the window sum is monotonic — expanding only increases it, shrinking only decreases it. I'll use a standard two-pointer approach: right pointer always advances, inner while shrinks when we exceed the budget. Time is O(n), space O(1)."

While coding: "For each new right element, I add it to the running sum. If we've exceeded B, I shrink from the left until we're back within budget. Then I record the window length."

After coding: "Let me trace through the example to verify. chunks = [4,2,1,3,5,2,1], B = 10..."

Likely follow-ups

Return the actual subarray, not just length?
Track best_left and best_right when updating curr_max. Return chunks[best_left:best_right+1].
What if chunks can be zero or negative?
Sliding window breaks — monotonicity is gone. Switch to prefix sum + hashmap approach, O(n) time, O(n) space.
Streaming version — chunks arrive one at a time?
Same algorithm. You don't need the full array — just maintain left, curr_sum, and curr_max as each chunk arrives. O(1) per chunk amortized.

7. Coding — Binary Search Template

Your weakness: returning mid after the loop. Never return mid.

# Leftmost >= target: answer is always lo
def binary_search(arr, target):
    lo, hi = 0, len(arr) - 1

    while lo <= hi:
        mid = (lo + hi) // 2
        if arr[mid] >= target:   # condition met — search LEFT
            hi = mid - 1
        else:                    # too small — discard left
            lo = mid + 1

    return lo if lo < len(arr) else -1   # always lo, never mid

Return rule: leftmost true → lo. Rightmost false → hi. Never mid.

8. Coding — BFS: All 3 Patterns

BFS has three templates. Know which one to reach for:

Know which BFS to use

PatternUse whenKey structure
A. Single deque + visitedShortest path (unweighted), flood fill, "can you reach X?"visited set, mark on enqueue
B. Two-queue swap"Level by level", min depth, "all nodes at distance K"Swap curr_queue ↔ next_queue per level
C. Single deque + indegreeTopological sort, dependency order, detect cycleindegree map, build → seed → BFS → cycle check

All three are O(V + E). All are BFS. Different templates for different questions.

A. Shortest Path / Flood Fill — deque + visited

The most basic BFS. Mark visited on enqueue, not dequeue — otherwise you process duplicates.

from collections import deque

def bfs_shortest(graph, start, target):
    queue = deque([start])
    visited = {start}             # mark on ENQUEUE, not dequeue
    dist = 0

    while queue:
        for _ in range(len(queue)):  # process current level
            curr = queue.popleft()
            if curr == target:
                return dist
            for nei in graph[curr]:
                if nei not in visited:
                    visited.add(nei)  # mark HERE, not when popping
                    queue.append(nei)
        dist += 1

    return -1  # unreachable
Why mark on enqueue? If you wait until dequeue, multiple nodes can push the same neighbor into the queue before any of them gets popped. You waste time processing duplicates.

B. Level-Order Traversal — two-queue swap

When you need to know which level you're on. Classic for trees.

def level_order(root):
    if not root: return []
    curr_queue = [root]
    result = []

    while curr_queue:
        next_queue = []           # collect ALL offspring
        level_vals = []
        for node in curr_queue:
            level_vals.append(node.val)
            if node.left:  next_queue.append(node.left)
            if node.right: next_queue.append(node.right)
        result.append(level_vals)
        curr_queue = next_queue   # kids become parents

    return result

C. Topological Sort — deque + indegree

More setup, but predictable: build → seed → BFS → cycle check.

from collections import deque

def topo_sort(nodes, edges):
    # 1. BUILD — graph + indegree (just parsing input)
    graph = {n: [] for n in nodes}
    indegree = {n: 0 for n in nodes}
    for post, pre in edges:
        graph[pre].append(post)
        indegree[post] += 1

    # 2. SEED — zero-indegree nodes (one line)
    queue = deque([n for n in nodes if indegree[n] == 0])
    order = []

    # 3. BFS — pop, record, decrement neighbors
    while queue:
        curr = queue.popleft()
        order.append(curr)
        for nei in graph[curr]:
            indegree[nei] -= 1
            if indegree[nei] == 0:
                queue.append(nei)

    # 4. CYCLE CHECK — one line
    return order if len(order) == len(nodes) else []

Topo sort needs two hashmaps — that's the graph

WhatWhy
graph[node] → [neighbors]Who comes after me?
indegree[node] → intHow many things must happen before me?

How to narrate (topo sort)

Before coding: "This is a topological sort problem. I'll use BFS with an indegree map. I need two hashmaps — an adjacency list for the graph and an indegree count per node. I'll seed the queue with all zero-indegree nodes, then BFS: pop, record, decrement neighbors, push any that hit zero. If the order doesn't cover all nodes, there's a cycle. Time is O(V + E)."

While coding: "First I build the graph and indegree from the edges. Now I seed the queue — these nodes have no dependencies, they're ready immediately. Now the BFS loop: pop from the left, add to order, for each neighbor decrement their indegree — if it hits zero, they're free to go. Finally, cycle check: if order length doesn't match node count, there's a cycle."
