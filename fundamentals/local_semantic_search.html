Local Semantic Search over Browser History

Information Retrieval Privacy-First

Summary

This is a retrieval problem, not a generation problem. We don't need an LLM — we need a lightweight bi-encoder for embedding and a vector index for search. That's what keeps it fast and private on-device.

The user types a natural language query (e.g., "dog training") and the system returns all semantically relevant browser history entries — including paraphrases like "puppy obedience school."

The Pipeline

Browse-time (background): ┌──────────────┐ ┌──────────────────────┐ ┌──────────────────┐ │ Page visited │ ──▶ │ Sentence Transformer │ ──▶ │ Local Vector DB │ │ title + URL │ │ (bi-encoder, ~30M) │ │ (FAISS / SQLite) │ │ + snippet │ │ encode → 384-d vec │ │ store embedding │ └──────────────┘ └──────────────────────┘ └──────────────────┘ Query-time: ┌──────────────┐ ┌──────────────────────┐ ┌──────────────────┐ │ User query: │ ──▶ │ Same encoder │ ──▶ │ ANN search │ ──▶ Top-K results │ "dog training"│ │ encode → 384-d vec │ │ cosine similarity│ └──────────────┘ └──────────────────────┘ └──────────────────┘

Key Concepts

Bi-Encoder

Query and documents are encoded independently by the same model. Documents are pre-encoded at browse time (background indexing); only the query is encoded at search time. This is what makes it fast.

Contrast with a cross-encoder, which takes (query, document) pairs jointly — more accurate but O(N) at query time, so impractical for search.

Dense Vector Embeddings

Each text is mapped to a fixed-size vector (e.g., 384-d float32). Semantically similar texts land close together in this space. "dog training" and "puppy obedience school" will have high cosine similarity even though they share no words.

Approximate Nearest-Neighbor (ANN) Search

Brute-force comparison against all vectors is O(N). ANN data structures (e.g., HNSW, IVF in FAISS) trade a tiny accuracy loss for sub-linear query time. For 10K–100K history entries, even brute force is fine.

Hybrid Search: Vector + BM25

Pure vector search can miss exact keyword matches; pure keyword search (BM25) misses paraphrases. Hybrid search combines both: run BM25 and vector search in parallel, then fuse the ranked lists (e.g., Reciprocal Rank Fusion).

Engineering Tradeoffs

Embedding Quality vs. Speed

Smaller model = faster inference but weaker semantic understanding. May miss "puppy obedience school" when searching "dog training." MiniLM-L6 (22M) is the sweet spot for on-device.

When to Embed

Background indexing at browse time. Amortize cost across browsing sessions. First search is instant. Alternative: lazy indexing on first query — bad UX.

Storage Budget

10K pages × 384-dim × float32 = ~15 MB. Trivial. Even 100K pages = ~150 MB. No concern on any laptop.

Privacy Guarantee

No API calls, no cloud. Model weights shipped with the browser. All inference via ONNX Runtime or WebAssembly (WASM). Data never leaves the device.

Where IR Sits in CS

IR is the field that produced Google Search, then evolved into:

  • Dense retrieval (2019+) — replaced BM25 with neural embeddings. This is what Mozilla wants.
  • RAG (2020+) — retrieve relevant docs, feed to an LLM. Every chatbot with "knowledge" uses this.
  • Recommendation systems — a special case of retrieval. Netflix recs = retrieve top-K items for a user embedding.

Retrieval is the glue between embedding knowledge and LLM applications.
