Flow Matching — Hands-On with GPU

Flow Matching MNIST B200

Built from actually training flow matching on a p6 B200 node, then asking every "but why?" until it clicked. This page follows my own path to understanding — so future-me can pick it up fast.

The North Star

Flow matching is nothing but learning a velocity field. The velocity means the magnitude and direction that brings you from noise to data. That's the entire goal.

noise (出发点) ──velocity (路)──▶ data (罗马) x0 x1 - x0 x1 The model doesn't learn Rome. It learns the roads.

条条大路通罗马 — but reversed. One Rome (the data distribution), infinite roads leading to it. The model learns ALL the roads. Give it any noise, it knows the way home.

The Entire Algorithm in 5 Lines

x0     = torch.randn_like(x1)                          # x0 = pure noise (出发点)
t      = torch.rand(b, device=device)                   # random position along the road, 0.0 to 1.0
x_t    = (1 - t) * x0 + t * x1                        # where you are at position t
target = x1 - x0                                       # the velocity (the road itself)
loss   = F.mse_loss(model(x_t, t), target)              # learn to predict the road from any position

No noise schedule, no score function, no reverse SDE. Just regression on velocities.

Clarification: b is batch size, not max steps. t = torch.rand(256) gives 256 random floats in [0, 1]. Each sample gets its own random position along the road. There is no loop over steps during training — just one random snapshot per sample.

What Exactly Is the Target?

The target is NOT "make x_t close to x1." It's the velocity — the road itself.

model(x_t, t)  →  predicted velocity  (what the model thinks the road is)
x1 - x0        →  true velocity       (what the road actually is)

MSE measures: "how wrong is the model's road prediction vs the actual road?"

The velocity is constant along the path

Because the path is a straight line:

x0 ─────────────────────────── x1 velocity = x1 - x0 everywhere At t=0.1: near noise, velocity = x1 - x0 At t=0.5: in middle, velocity = x1 - x0 At t=0.9: near data, velocity = x1 - x0

What t changes is the difficulty, not the target

t≈0: model sees mostly noise → predict velocity (hard!) t≈0.5: model sees half noise/data → predict velocity (medium) t≈1: model sees mostly clean data → predict velocity (easy) Same target every time. Different input difficulty.

Each (noise, data) pair has its own velocity. x1 - x0 differs for every pair. The model learns a function: given any blurry input at any t, predict the right velocity for that particular trajectory.

How Does It Know If Noise Becomes a 1 or a 9?

It doesn't decide. Nobody decides — not even the model. The digit emerges.

The model just says "given this input at this timestep, nudge pixels this direction." Purely local, one step at a time, no planning.

Step 0: sees noise. No idea it'll be a 9. Step 10: sees vague blob. Still no idea. Step 25: sees round thing with tail. Starting to commit. Step 40: clearly a 9. Just refining. Step 50: done.

Like a ball rolling downhill. The ball doesn't "know" where it ends up. The landscape (velocity field) determines the path. The starting position (noise) determines which valley.

Same noise + same model = exact same digit every time. The outcome is determined the moment you pick the noise. It is what it is.

Why Is This Generative?

At inference there's no ground truth. You get a random starting point and the learned roadmap leads you somewhere that makes sense — but the output may not exist in any training data.

The model never memorized specific digits. It learned the velocity field — the general structure of "how to get from noise to digit-like things." New noise follows the learned roads and arrives at a plausible digit that never existed before.

The wisdom analogy: Training data = thousands of lived experiences. Velocity field = distilled wisdom — not any specific life, but the patterns. Noise = a new person born into unique circumstances. Output = their life — shaped by the wisdom, but entirely their own. History doesn't repeat itself, but it rhymes. That's literally what a generative model does.

Part 2: Build It Yourself — Sine Wave Flow Matching

MNIST was "run someone else's code." This part is "build it from scratch, break it, debug it, understand why." Every mistake here taught something real.

The Setup

Goal: train flow matching to generate 64-point chunks of a sine wave. Simplest possible 1D signal. No images, no U-Net — just an MLP, a sine function, and the same 5-line algorithm.

seq_len = 64
def data_gen(bs=32):
    x = torch.linspace(0, 2 * math.pi, 200)
    starts = torch.randint(0, 200 - seq_len, (bs,))
    return torch.stack([torch.sin(x[s:s+seq_len]) for s in starts])  # [32, 64]

Each sample is a 64-dim vector — a chunk of sine wave at a random phase. The model should learn to generate smooth sinusoidal curves from noise.

How to Feed (x_t, t) Into an MLP

Flow matching needs both x_t and t as input. An MLP only takes one tensor. Solution: concatenate.

# x_t: [B, 64]   t: [B, 1]
inp = torch.cat([x_t, t], dim=-1)   # [B, 65]

# So fc1 must accept 65, not 64:
self.fc1 = nn.Linear(data_dim + 1, hidden)  # +1 for t

Why does the model need t at all? Because the same x_t can mean different things at different t. A blurry image at t=0.95 means "almost done, nudge gently." The same blur at t=0.05 means "long way to go, push hard." Without t, the model can't tell where it is on the road.

PyTorch Syntax Gotchas I Hit

1. F.relu() vs nn.ReLU()

# WRONG — F.relu is a function, can't call it in __init__
self.act = F.relu()   # TypeError!

# RIGHT — use it directly in forward
return self.fc2(F.relu(self.fc1(x)))

# OR store as module
self.act = nn.ReLU()  # this is a module, OK in __init__

2. torch.cat dimension mismatch

# WRONG — [128] and [128, 64] can't cat
t = torch.rand(128)                     # shape [128]
torch.cat([x, t], dim=-1)               # Error!

# RIGHT — make t 2D first
t = torch.rand(128).unsqueeze(-1)       # shape [128, 1]
torch.cat([x, t], dim=-1)               # [128, 65] ✓

3. Forgetting dim=-1 in torch.cat

# Default is dim=0 — concatenates along BATCH, not features
torch.cat([a, b])        # stacks batches: [256, 64] — wrong!
torch.cat([a, b], dim=-1) # appends features: [128, 65] — right!

4. unsqueeze options

t = torch.rand(128)       # [128]
t.unsqueeze(-1)            # [128, 1] ← want this
t.unsqueeze(0)             # [1, 128] ← wrong dim
t[:, None]                 # [128, 1] ← shorthand, same thing
t.view(-1, 1)             # [128, 1] ← also works

5. loss.item() not loss.value

# WRONG
print(loss.value)    # AttributeError: 'Tensor' has no attribute 'value'

# RIGHT
print(loss.item())   # extracts Python float from scalar tensor

6. fan_in must match the cat'd dimension

# After cat([x_t, t], dim=-1), last dim = data_dim + 1
# fc1's in_features MUST equal data_dim + 1
self.fc1 = nn.Linear(data_dim + 1, hidden)  # not data_dim!

Bug #1: Data Was Flat

First attempt used linspace(0, 2π, 10000) — 10,000 points over one cycle. Each 64-point chunk covered only 0.04 radians. That's a flat line.

10000 points over 2π: each chunk = 64/10000 × 2π = 0.04 rad ≈ flat line 200 points over 2π: each chunk = 64/200 × 2π = 2.0 rad ≈ 1/3 of wave ✓

The model learned perfectly — it generated perfect flat lines. Garbage in, garbage out. Always visualize your training data before blaming the model.

Bug #2: Loss Won't Go to Zero

Loss plateaued around 0.3. Felt wrong — sine is simple, shouldn't the model nail it?

No. Even a perfect model has nonzero MSE. The target x1 - x0 depends on random noise x0. For the same x_t and t, many different (x0, x1) pairs could have produced it. The model can only predict the average velocity. The variance around that average is irreducible.

Lesson: Don't judge flow matching by loss value. Judge by generated samples. Loss ~0.3 with beautiful sine waves = success.

The Big Lesson: Architecture Is Everything

Same flow matching, same data, same training. Only the model changed:

MLP (4 layers, SiLU, 50K steps)

Jagged, noisy, vaguely downward-trending. Learned the value range [-1, 1] but not the smoothness. MLP treats each of the 64 dimensions independently — it doesn't know position 30 is next to 31.

Conv1d (3 layers, kernel=7, 50K steps)

Smooth sinusoidal curves at different phases. Learned the actual wave shape. Conv1d with kernel=7 means each output looks at 7 neighbors — local smoothness is built in.

class ConvVelocity(nn.Module):
    def __init__(self, hidden=128):
        super().__init__()
        self.t_mlp = nn.Sequential(nn.Linear(1, hidden), nn.SiLU(), nn.Linear(hidden, hidden))
        self.conv1 = nn.Conv1d(1, hidden, 7, padding=3)
        self.conv2 = nn.Conv1d(hidden, hidden, 7, padding=3)
        self.conv3 = nn.Conv1d(hidden, 1, 7, padding=3)

    def forward(self, x, t):
        t_emb = self.t_mlp(t)              # [B, hidden]
        h = x.unsqueeze(1)                  # [B, 1, 64]
        h = F.silu(self.conv1(h))           # [B, hidden, 64]
        h = h + t_emb.unsqueeze(-1)         # inject t into every position
        h = F.silu(self.conv2(h))           # [B, hidden, 64]
        h = self.conv3(h)                   # [B, 1, 64]
        return h.squeeze(1)                 # [B, 64]

The framework is 5 lines. The architecture is everything. This is exactly why real systems use U-Nets, DiTs, and attention — not because flow matching requires it, but because the generated output quality depends entirely on the model's inductive bias. Flow matching doesn't care what's inside model().

Practical Notes (Sine Wave)

  • Visualize training data first. If your 64-point chunks look flat, the model will generate flat lines perfectly.
  • ReLU → SiLU for smooth data. ReLU produces jagged outputs. SiLU is smooth and works better for continuous signals.
  • 2-layer MLP is too shallow for 64-dim data. 3-4 layers minimum.
  • lr=1e-3 with Adam worked well. 1e-4 was too slow for 10K iterations.
  • 50K iterations needed for MLP to show any structure. Conv1d looked good by 10K.

Golden 1 Min

Flow matching is just five lines of training code:

x0     = torch.randn_like(x1)              # pure noise
target = x1 - x0                           # ground truth velocity
t      = torch.rand(bs)                    # random snapshot in [0, 1]
x_t    = (1 - t) * x0 + t * x1            # linear interpolation
loss   = F.mse_loss(model(x_t, t), target)  # predict velocity from any snapshot

You're learning a model to predict the velocity field that approximates the ground truth velocity, which is x1 minus x0. x0 is the noise, x1 is the destination. Assume the shortest path — the velocity gives you the direction and how fast to move there. During training, at any arbitrary snapshot, the model learns to predict the move that gets you to the North Star.

For flow matching, training and inference behave differently. During training, there's no concept of steps — it just learns to predict the velocity from any arbitrary snapshot. But during inference, you specify a number of steps first, then use iterative Euler steps to integrate the velocity the model gives you at each step. You always start from pure noise with a predefined number of steps. If the model is well trained, it gives you the velocity to move toward the real data, one step at a time.

# Inference: Euler integration
x = torch.randn(B, D)
n_step = 20
dt = 1.0 / n_step
for i in range(n_step):
    t = torch.full((B, 1), i * dt)
    v = model(x, t)
    x += dt * v
