Flow Matching — Hands-On with GPU

Flow Matching MNIST B200

A hands-on tutorial from actually training flow matching on a p6 B200 node. Not theory-first — we ran it, broke it, fixed it, and asked "but why?" along the way.

The Entire Algorithm in 5 Lines

This is everything. No noise schedule, no score function, no reverse SDE. Just regression on velocities.

x0     = torch.randn_like(x1)                          # sample noise
t      = torch.rand(b, device=device)                   # random timestep ~ U(0,1)
x_t    = (1 - t) * x0 + t * x1                        # straight line interpolation
target = x1 - x0                                       # velocity (constant!)
loss   = F.mse_loss(model(x_t, t), target)              # regress on velocity

Sampling is just Euler integration from noise to data:

x = torch.randn(n, 1, 28, 28)                           # start from pure noise
for i in range(steps):
    t = torch.full((n,), i / steps)
    x = x + model(x, t) * (1 / steps)                   # Euler step

What Does Training Actually Do?

Not denoising. It's learning a velocity field.

What the Model Sees During Training

The model input is NOT pure noise. It's the interpolated mix at a random timestep:

x_t = (1-t)*noise + t*digit t=0.0 → pure noise (model sees garbage) t=0.3 → mostly noise (model sees vague shape) t=0.7 → mostly digit (model sees blurry digit) t=1.0 → pure digit (model sees clean digit)

The model takes (x_t, t) and outputs the velocity — same shape, 28×28. It's saying "nudge each pixel this much toward the data."

Over millions of samples at random t values, the model learns the velocity everywhere along the noise→data path. But it never sequentially walks from 0 to 1 during training.

How Does It Know If Noise Becomes a 1 or a 9?

It doesn't decide upfront. The noise itself determines the digit.

The model learned a velocity field that covers the entire space. Different regions of noise space flow to different digits:

Noise space Data space region A ────velocity field────▶ "1" region B ────velocity field────▶ "7" region C ────velocity field────▶ "9" region D ────velocity field────▶ "3" ...

The model doesn't look at noise and think "this is a 9." It just says "given this input at this timestep, nudge the pixels this direction." Then at the next step, "ok now nudge this direction." Purely local — one step at a time, no planning.

Step 0: model sees noise. Has no idea it'll be a 9. Step 10: model sees vague blob. Still no idea. Step 25: model sees something round-ish with a tail. Starting to commit. Step 40: clearly a 9 now. Model is just refining details. Step 50: done.

It's like a ball rolling downhill. The ball doesn't "know" where it'll end up. The landscape (velocity field) determines the path. The starting position (noise) determines which valley it rolls into. The digit emerges. It's not chosen.

If you run the same noise twice with the same model, you get the exact same digit every time. Different noise → different digit. The randomness is only in your initial sample.

From Noise to 10 Digits

The velocity field partitions noise space into basins — one flowing toward each digit. And not just 10 — infinitely many variations within each. Different 7s with different slants, different 3s with different curves.

The model learned the entire distribution of MNIST, not just 10 templates. Each noise vector flows to a unique handwritten digit that looks like it could've been in the training set, but never was.

That's generative modeling. From one simple distribution (Gaussian noise) to a complex one (handwritten digits), connected by a learned velocity field.

What Makes It Useful: Conditioning

The unconditional version (what we trained) generates random digits nobody asked for. The power comes when you condition it:

ImageText promptThat exact imageStable Diffusion, FLUX, DALL-E 3

The pattern is always the same:

Random noise + condition → desired output Unconditional: pred = model(x_t, t) "go wherever the noise takes you" Conditional: pred = model(x_t, t, label=9) "go toward a 9 specifically"

Our MNIST demo is the engine — conditioning is the steering wheel.

Real Training Run: MNIST on B200

Trained on a single p6 B200 node. 60,000 MNIST images, 3.6M parameter U-Net, 100 epochs.

Key observation: Loss plateaus around epoch 30-40. Visual quality converges faster than the loss — the last 0.01 of MSE is sub-pixel refinement you can barely see. In real systems, people often stop training earlier and spend compute on scaling the model or data instead.

What the progression shows

Epoch 10: Blurry blobs → velocity predictions are noisy, ODE paths wander → blurry results Epoch 30: Clean digits → velocities are accurate, paths go straight from noise → digit Epoch 100: Crystal clear → velocity field is well-learned, Euler integration traces clean paths

This progression directly visualizes what flow matching is doing: as the velocity field gets more accurate, the ODE paths straighten out and the generated samples sharpen.

Flow matching needs fewer steps because the paths are approximately straight lines. Even a crude Euler integrator with 50 steps gets you there. DDPM's paths are curved (following a noise schedule), requiring more steps to trace accurately.

Full Training Script

Zero dependencies beyond torch and numpy. Loads MNIST from raw gzipped files, writes PNG grids using pure Python. Runs on air-gapped GPU nodes.

# ── Flow Matching core ────────────────────────────────────

def flow_matching_loss(model, x1):
    b = x1.shape[0]
    x0 = torch.randn_like(x1)
    t = torch.rand(b, device=x1.device)
    t_ = t[:, None, None, None]
    x_t = (1 - t_) * x0 + t_ * x1
    return F.mse_loss(model(x_t, t), x1 - x0)


# ── Sampling (Euler integration) ──────────────────────────

@torch.no_grad()
def sample(model, n=64, steps=50, device="cuda"):
    x = torch.randn(n, 1, 28, 28, device=device)
    dt = 1.0 / steps
    for i in range(steps):
        t = torch.full((n,), i * dt, device=device)
        x = x + model(x, t) * dt
    return x.clamp(-1, 1)


# ── Training loop ─────────────────────────────────────────

model = UNet(in_ch=1, base_ch=64).to(device)       # ~3.6M params
opt = torch.optim.AdamW(model.parameters(), lr=3e-4)

for epoch in range(100):
    for (x1,) in dataloader:
        x1 = x1.to(device)
        loss = flow_matching_loss(model, x1)
        opt.zero_grad()
        loss.backward()
        opt.step()

    if (epoch + 1) % 10 == 0:
        imgs = sample(model, n=64, steps=50)
        save_grid_png(imgs, f"epoch{epoch+1:03d}.png")

The U-Net is a standard encoder-decoder with ResBlocks and sinusoidal timestep embeddings. Nothing diffusion-specific — any architecture that takes (x_t, t) and outputs same-shape works. In production: replace with a DiT (Diffusion Transformer) for better scaling.

Practical Notes from the Run

Air-gapped GPU nodes

Training nodes often have no internet. Download data locally, kubectl cp to the pod. MNIST is 11MB — trivial to sync. Avoid any dependency that phones home (torchvision downloads, HuggingFace hub).

No torchvision on Megatron containers

LLM training images don't ship torchvision. Load MNIST from raw .gz files with gzip + struct. Write PNGs with pure Python (zlib + minimal PNG chunk format). Zero external dependencies.

GroupNorm gotcha

nn.GroupNorm(8, 3) fails because 3 isn't divisible by 8. Fix: nn.GroupNorm(min(8, in_ch), in_ch). The first ResBlock gets in_ch=3 (or 1 for MNIST).

Convergence

MNIST converges fast — loss plateaus by epoch 30-40. The model has excess capacity (3.6M params for 28×28 grayscale). For harder tasks, you'd need more capacity and data, not more epochs.

What to Try Next

On the same node, today

  • More ODE steps at sampling — change steps=50 to 100 or 200. Compare quality. Flow matching with straighter paths should need fewer steps.
  • Optimal transport paths — pair noise to data by nearest neighbor in each mini-batch. Makes paths even straighter.
  • Class-conditional generation — feed the digit label as an extra input. Now you can ask for a specific digit.
  • Replace U-Net with DiT — transformer with AdaLN conditioning on timestep. That's what F5-TTS and modern video models use.

Scaling up

  • Speech: Clone F5-TTS — production-quality speech flow matching. DiT backbone, text conditioning, proper vocoder. Single p6 node is enough for a conference paper.
  • Video: Clone Open-Sora-Plan — most complete open training pipeline for video DiT.
  • Meta's library: facebookresearch/flow_matching — OT paths, Riemannian FM, discrete FM for text.
  • Theory: Flow Matching Guide and Code (Lipman et al.) — the definitive reference.
