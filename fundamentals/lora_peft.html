LoRA / PEFT

Parameter-Efficient Fine-Tuning

What LoRA actually does

A pre-trained weight matrix W has shape (d_out, d_in) — e.g. (4096, 4096) = 16.7M parameters for one layer. LoRA freezes W entirely and adds two small matrices:

# Original forward pass:
y = W @ x                        # W: (4096, 4096)  — 16.7M params, FROZEN

# LoRA forward pass:
y = W @ x + (B @ A) @ x          # A: (r, 4096), B: (4096, r)
                                  # r = rank, typically 4-64
                                  # Trainable params: 2 × r × 4096

# Example with rank 8:
#   A: (8, 4096)   = 32,768 params
#   B: (4096, 8)   = 32,768 params
#   Total: 65,536 params per layer  (vs 16.7M original = 0.4%)

The key insight: the weight update ΔW = B × A is constrained to be low-rank. This means LoRA can only make changes that lie in an r-dimensional subspace. For adaptation tasks (new speaker, new domain), this is usually enough — the "direction" of the change is simple even if the original model is huge.

Which layers get LoRA?

Common choiceLayers adaptedWhy
Attention only (most common)Wq, Wv projectionsThese control "what to attend to" and "what to extract" — most task-specific
Attention + FFNWq, Wv, Wup, WdownMore capacity, sometimes needed for larger domain shifts
All linear layersEvery nn.LinearMaximum flexibility, but slower and more parameters

For TTS/ASR voice adaptation, attention-only (q, v) is usually sufficient. The model already knows how to speak — it just needs to learn a new voice identity, which is a low-rank change.

Zero-shot is "buy," LoRA is "customize," full fine-tune is "build from scratch." Most production use cases start with zero-shot and only move to LoRA when consistency requirements demand it.

Beyond LoRA: the PEFT family

MethodHow it worksWhen to use
LoRALow-rank additive update to weight matricesDefault choice. Works well almost everywhere.
QLoRALoRA on a 4-bit quantized base modelWhen GPU memory is tight (e.g., fine-tuning 7B+ models on a single GPU)
Adapter layersInsert small bottleneck layers between existing layersOlder approach, largely superseded by LoRA
Prefix tuningPrepend learnable "virtual tokens" to the inputWhen you can't modify model weights at all

Interview story: Pruning + LoRA recovery

Your experience: Wanda pruning on LLaMA-7B → 50% unstructured sparsity → performance drops → LoRA recovery (rank 8, q/v projections only, 0.06% of params) → recovered most of the original performance.

Why this matters for the role: Same principle applies to speech models. A TTS or ASR model needs to be deployed on-device or at scale — pruning compresses it, LoRA recovers quality and adapts to the target domain. The insight is that pruning removes redundant capacity, and LoRA adds back task-specific capacity in a much smaller subspace.

# Wanda pruning + LoRA recovery pipeline
model = load("llama-7b")                   # 7B params

# Step 1: Prune — remove 50% of weights by importance
pruned = wanda_prune(model, sparsity=0.5)  # 3.5B nonzero params
# Performance drops: perplexity increases ~15-20%

# Step 2: LoRA recovery — add low-rank adapters
lora = add_lora(pruned, rank=8, targets=["q_proj", "v_proj"])
# Trainable params: ~4M  (0.06% of 7B)

# Step 3: Fine-tune LoRA on target task
train(lora, data, epochs=3)
# Performance recovers to within ~2% of original unpruned model

# Result: 50% smaller model, 0.06% extra params, ~98% original quality
