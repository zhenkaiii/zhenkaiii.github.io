TTS Landscape 2025-2026

Text-to-Speech

Modern TTS has converged on three paradigms, each with a distinct generative mechanism. Understanding which to use — and when — is the core "build vs buy" decision for production speech systems.

Paradigm 1: Autoregressive Codec LM

Treat speech as a language of audio tokens

Text (string) → Phoneme conversion → phoneme sequence, e.g. [HH AH L OW] → Transformer LM → discrete audio tokens (integers), one at a time, like GPT predicting the next word → Audio codec decoder → raw waveform (the sound you hear)

Same architecture as GPT, just predicting audio tokens instead of text tokens. A neural audio codec (e.g. EnCodec) compresses waveforms into a sequence of integers — each integer represents ~20ms of sound. The Transformer learns to predict these integers one by one. Then the codec's decoder converts the integers back into a waveform.

Meanwhile, a reference audio clip (3-10 sec) is also encoded into tokens and prepended as a "prompt" — so the model copies that voice, just like giving GPT a few examples makes it follow the pattern.

ModelKey detail
VALL-E (Microsoft)First to prove codec LM works for TTS. AR + NAR transformer stages.
Bark (Suno)Open-source, three-stage transformer (semantic → coarse → fine tokens).
XTTS (Coqui)Open-source, good zero-shot voice cloning, practical for production.
SPEAR-TTS (Google)Semantic tokens → acoustic tokens, two-stage decoupling.

Pros: Natural prosody, strong zero-shot cloning, simple "just predict next token" paradigm.

Cons: Slow (autoregressive = one token at a time), hallucination/repetition artifacts, hard to stream.

Typical latency: ~500ms-2s per utterance.

VALL-E Inference: Step-by-step Pseudocode

Generating 2 seconds of speech from "Hello world", cloning a 3-second reference voice.

VALL-E uses EnCodec with 8 RVQ layers at 75 Hz. It has two stages: an AR transformer generates the first (coarsest) RVQ layer, then a NAR transformer fills in the remaining 7 layers in parallel.

# ── Key rates ─────────────────────────────────────────────
sample_rate     = 24,000 Hz
codec_frame_rate = 75 Hz          # EnCodec frames per second
n_rvq_layers    = 8               # 8 quantization layers (coarse → fine)
codebook_size   = 1,024           # each RVQ layer has 1024 codes

# So: 1 codec frame = 8 integers (one per RVQ layer) = ~13ms of audio
# The full code matrix for 2s of audio: (8, 150) — 8 layers × 150 frames
# ── Step 0: Frontend ──────────────────────────────────────

text = "Hello world, this is a test."

phonemes = g2p(text)                    # rule-based grapheme-to-phoneme
# phonemes: (1, 20)                    int IDs, e.g. [HH, AH, L, OW, ...]

ref_audio = load("reference.wav")       # 3-second clip at 24kHz

ref_codes = encodec.encode(ref_audio)   # neural audio codec encoder
# ref_codes: (8, 225)                  8 RVQ layers × (3s × 75 Hz)
#   Layer 0: coarsest — captures phoneme identity, rough pitch
#   Layer 7: finest — captures subtle texture, breathiness
# ── Stage 1: AR Transformer — generate coarse codes (SLOW) ─
# Only generates RVQ layer 0 (the coarsest layer).
# This is where prosody, rhythm, and phoneme timing are decided.

# Build prompt: phonemes + reference layer-0 codes
ar_input = concat([
    phoneme_embeds,                     # (1, 20, 1024)   what to say
    ref_code_embeds,                    # (1, 225, 1024)  sound like this
])
# ar_input: (1, 245, 1024)

# Autoregressive loop — one code at a time, like GPT
generated_layer0 = []
for step in range(150):                 # 2s × 75 Hz = 150 frames
    hidden = ar_transformer(ar_input, kv_cache)   # (1, 1, 1024)
    logits = output_head(hidden)                  # (1, 1024) over codebook
    code   = sample(logits)                       # scalar int ∈ [0, 1024)
    generated_layer0.append(code)

# generated_layer0: (1, 150)           int — coarse codes for 2s
# These capture: WHICH phonemes, HOW LONG each lasts, pitch contour
# But audio from only layer 0 would sound very rough/robotic
# ── Stage 2: NAR Transformer — fill in fine codes (FAST) ───
# Generates layers 1-7 ALL AT ONCE (non-autoregressive).
# Each layer adds more acoustic detail.

code_matrix = zeros(8, 150)             # 8 layers × 150 frames
code_matrix[0] = generated_layer0      # from Stage 1

for layer in range(1, 8):               # layers 1, 2, ..., 7
    # NAR sees: phonemes + all codes generated so far
    nar_input = concat([phonemes, code_matrix[:layer]])

    new_codes = nar_transformer(nar_input)  # predicts ALL 150 codes at once
    # new_codes: (1, 150)               entire layer in one forward pass!

    code_matrix[layer] = new_codes

# code_matrix: (8, 150) int — full RVQ code matrix
#   Layer 0: phoneme identity, pitch          (from AR, slow)
#   Layer 1: spectral shape                   (from NAR, fast)
#   ...
#   Layer 7: fine texture, breathiness        (from NAR, fast)
# ── Stage 3: EnCodec Decoder — codes → waveform ───────────
# The codec decoder is a neural network that reverses the encoding.
# Each RVQ layer's codes get looked up in their codebook, summed,
# then upsampled through transposed convolutions.

quantized = sum([codebook[l].lookup(code_matrix[l]) for l in range(8)])
# quantized: (1, 128, 150)             continuous vectors (sum of 8 codebook lookups)

waveform = encodec.decode(quantized)
# waveform: (1, 48000)                 150 frames × 320 samples/frame = 48,000
#   = 48,000 ÷ 24,000 Hz = 2.0 seconds of audio
# ── Why VALL-E is slow ────────────────────────────────────
# Stage 1 (AR):  150 sequential steps for layer 0     ← bottleneck
# Stage 2 (NAR): 7 parallel forward passes             ← fast
# Stage 3 (Decode): 1 forward pass                     ← fast
#
# 2s of audio = 150 AR steps. At ~10ms per step = ~1.5s latency.
# You wait longer than the audio itself takes to play!

Paradigm 1b: Non-AR Token LM

Same discrete tokens, but generated in parallel

Text (string) → Semantic model → coarse semantic tokens (AR or external) → Non-AR masked Transformer → all acoustic tokens at once (parallel, like BERT-style masked prediction) → Audio codec decoder → waveform

Same representation as Paradigm 1 (discrete codec tokens), but the generation is non-autoregressive — tokens are predicted in parallel using iterative masked prediction (like MaskGIT for images), not one at a time. This removes the AR speed bottleneck while keeping the discrete token framework.

ModelKey detail
SoundStorm (Google)Parallel token generation via masked prediction. Requires semantic tokens from a separate model (e.g., SPEAR-TTS). Very fast.

Pros: Much faster than AR (parallel generation), same discrete token quality.

Cons: Needs a separate semantic token model upstream. Less studied than AR approach.

This is technically a 4th family. We group it under Paradigm 1 because the representation (discrete codec tokens) is the same — only the generation strategy differs (parallel vs sequential).

Paradigm 2: Flow-matching / Diffusion

Generate speech via continuous denoising

Text (string, e.g. "Hello world") → G2P tokenizer → phoneme IDs (integers, e.g. [14, 3, 27, 42]) — rule-based, not a neural network → Text encoder (Transformer) → contextual vectors (one per phoneme, each ~256-512 dims) — encodes not just "what phoneme" but "how it relates to neighbors" → Flow-matching generator (DiT or UNet) → mel spectrogram (a 2D matrix: time × 80 frequency bins) — a heat map of "how it sounds" → Vocoder (HiFi-GAN / BigVGAN) → raw waveform (the actual audio signal you hear)

Note: the tokenizer and the text encoder are different things. The tokenizer (G2P) is a simple converter: string → integer IDs. The text encoder is a neural network (Transformer) that reads those IDs and outputs rich contextual vectors — capturing not just "this is phoneme L" but "this L sits between two vowels in an unstressed syllable, so it should sound softer."

The flow-matching generator (a DiT or UNet, not the same Transformer) takes those vectors and iteratively transforms random noise into a mel spectrogram — a 2D representation of audio that looks like a heat map of frequency over time. Finally, a vocoder neural network converts that spectrogram into an actual audio waveform.

Voice cloning: a speaker embedding (a single vector, ~256 dims, extracted from a reference clip) is fed as a condition to the generator, telling it whose voice to use.

ModelKey detail
F5-TTSFlow-matching + DiT, strong zero-shot, non-autoregressive.
VoiceBox (Meta)Flow-matching, infilling capability (can edit/replace parts of speech).
NaturalSpeech 3 (Microsoft)Diffusion with factorized codec representations.
Grad-TTSEarly diffusion TTS, score-based generation.
Stable Audio (Stability)Latent diffusion for general audio, not just speech.

Pros: Highest quality, non-autoregressive (generate full utterance at once), fewer hallucination artifacts.

Cons: Multi-step inference (6-50 steps), latency depends on step count, needs separate vocoder.

Typical latency: ~100ms-1s depending on step count (4 steps ~100-200ms, 20 steps ~500ms-1s).

Diffusion vs Flow-matching

DiffusionFlow-matching
ProcessStochastic (SDE)Deterministic (ODE)
Steps needed20-50 for quality6-10 (graceful degradation with fewer)
Why fewer steps workStochastic noise accumulatesODE integration stays on trajectory
Distillation target~4-8 steps~1-4 steps (consistency models)

Flow-matching dominates new TTS research because it's faster and more controllable. Most "diffusion TTS" papers in 2025-2026 are actually flow-matching.

F5-TTS Inference: Step-by-step Pseudocode

Generating 2 seconds of speech from "Hello world", cloning a 3-second reference voice.

F5-TTS is radically simple: no phoneme conversion, no duration model, lightweight CNN text encoder (ConvNeXt instead of Transformer). It treats TTS as a speech infilling task — given reference audio with text, fill in the blank for new text.

# ── Key rates ─────────────────────────────────────────────
sample_rate      = 24,000 Hz
mel_frame_rate   = 86.1 Hz        # hop_size=256, so 24000/256 ≈ 86
mel_bins         = 100            # F5-TTS uses 100 mel bins (not 80)
n_ode_steps      = 32             # default NFE (can be reduced with Sway Sampling)
# ── Step 0: Frontend — deliberately minimal ───────────────

text_to_generate = "Hello world, this is a test."
ref_text         = "This is the reference transcript."
ref_audio        = load("reference.wav")       # 3-second clip

# Convert text to CHARACTER sequence (not phonemes!)
# F5-TTS works at the character level — no G2P needed
gen_chars = list("hello world this is a test")  # lowercase, stripped
ref_chars = list("this is the reference transcript")

ref_mel = mel_spectrogram(ref_audio)
# ref_mel: (1, 100, 258)               3s × 86 frames/s ≈ 258 frames

gen_duration_frames = int(2.0 * 86.1)   # target: 2s
# gen_duration_frames: 172
# ── Step 1: Pad text with filler tokens ───────────────────
# Key F5-TTS trick: pad the text to EXACTLY match the audio length.
# No duration model needed — the model learns alignment implicitly!

ref_char_ids  = char_to_id(ref_chars)    # (26,) int
gen_char_ids  = char_to_id(gen_chars)    # (25,) int

# Pad each text to match its mel length using a special FILLER token
ref_padded  = pad_with_filler(ref_char_ids,  target_len=258)   # (258,)
gen_padded  = pad_with_filler(gen_char_ids,  target_len=172)   # (172,)

# Concatenate: [ref_text_padded | gen_text_padded]
text_sequence = concat([ref_padded, gen_padded])
# text_sequence: (430,)                258 + 172 characters/fillers

# Refine through ConvNeXt V2 blocks (small CNN, not a Transformer)
text_features = convnext(embed(text_sequence))
# text_features: (1, 430, 1024)        now same time resolution as mel
# ── Step 2: Set up the infilling task ─────────────────────
# Concatenate reference mel + masked region (zeros for generation)

input_mel = concat([
    ref_mel,                            # (1, 100, 258)  real reference
    zeros(1, 100, 172),                 # (1, 100, 172)  blank to fill in
], dim=time)
# input_mel: (1, 100, 430)

# The model sees: "here is audio for the reference text,
#                  now fill in audio for the new text"
# ── Step 3: ODE solver with DiT ───────────────────────────
# Start from noise in the generation region. Reference region stays fixed.

x = randn(1, 100, 172)                 # noise for generation region only

for step in range(32):                  # 32 ODE steps (Sway Sampling schedule)
    t = sway_schedule(step, 32)         # non-uniform timesteps (more steps near t=0)

    # DiT (Diffusion Transformer) input:
    #   - noisy mel x_t (generation region)
    #   - reference mel (real, frozen)
    #   - text features (aligned by position)
    #   - timestep embedding
    full_mel = concat([ref_mel, x], dim=time)
    # full_mel: (1, 100, 430)

    velocity = dit(full_mel, text_features, t)
    # velocity: (1, 100, 430)           but we only update generation region

    gen_velocity = velocity[:, :, 258:]  # (1, 100, 172)
    x = x + dt * gen_velocity            # Euler step

# x: (1, 100, 172) — generated mel spectrogram for 2s
# ── Step 4: Vocoder — mel → waveform ──────────────────────

waveform = vocos(x)                     # Vocos vocoder (used by F5-TTS)
# waveform: (1, 44032)                 172 frames × 256 hop = 44,032 samples
#   = 44,032 ÷ 24,000 Hz ≈ 1.8 seconds
# ── Why F5-TTS is elegant ─────────────────────────────────
# No G2P:          works on raw characters (even Chinese characters)
# No duration model: filler padding lets the model learn alignment
# Lightweight text encoder: ConvNeXt CNN instead of Transformer
# No AR loop:       entire mel generated via ODE (parallelizable)
#
# Speed: 32 steps × 1 DiT forward pass each
#   With Sway Sampling: can reduce to 6-8 steps with minimal quality loss
#   With distillation: down to 1-4 steps

Paradigm 3: End-to-end Single-pass

One forward pass, waveform out

Text (string) → G2P tokenizer → phoneme IDs (integers) → Text encoder (Transformer + speaker embedding) → hidden vectors htext (one per phoneme, encoding content + speaker identity) → Duration predictor → integer durations d (how many audio frames each phoneme lasts, e.g. [2, 2, 1]) → Expand htext by durations + Normalizing flow → latent representation z (continuous vectors in a learned latent space) → Decoder (built-in HiFi-GAN) → raw waveform directly (no separate vocoder needed)

Everything happens in one model, one forward pass. Inside, it combines three techniques: a VAE (variational autoencoder) that learns a compact latent space for speech, normalizing flows that make the latent distribution flexible enough to capture real speech variation, and a GAN discriminator that pushes the output waveform to sound realistic. The decoder is essentially a built-in vocoder.

ModelKey detail
VITSVAE + normalizing flows + adversarial training. Integrated vocoder. Stochastic duration predictor.
VITS2Improved duration predictor (adversarial training), better Transformer blocks, more natural prosody.

Voice cloning: Speaker embedding lookup table — each known speaker gets a learned vector. Speaker must be seen during training. No zero-shot capability.

Pros: Fastest inference (~30ms single pass), no separate vocoder needed, fully end-to-end.

Cons: No zero-shot voice cloning (speaker must be in training set), weaker speaker generalization, prosody modeling less flexible than AR models.

Quality can be very high for known speakers. Best choice when latency is the absolute priority and the speaker set is fixed.

VITS Inference: Step-by-step Pseudocode

Generating 2 seconds of speech from "Hello world" using a known speaker (speaker #7 from training data).

VITS does everything in one forward pass — no iterative ODE, no autoregressive loop. Text goes in, waveform comes out. The key trick: a normalizing flow transforms a simple Gaussian distribution into the complex distribution of real speech, and a built-in HiFi-GAN decoder generates the waveform directly (no separate vocoder).

# ── Key rates ─────────────────────────────────────────────
sample_rate      = 22,050 Hz      # VITS default (not 24k)
hop_size         = 256
frame_rate       = 86 Hz          # 22050 / 256 ≈ 86 frames/sec
hidden_dim       = 192            # latent / inter-channel dim
n_speakers       = 109            # multi-speaker: lookup table, not zero-shot
# ── Step 0: Frontend ──────────────────────────────────────

text = "Hello world, this is a test."

phoneme_ids = g2p(text)                 # rule-based grapheme-to-phoneme
# phoneme_ids: (1, 20)                 int IDs for [HH, AH, L, OW, ...]

speaker_id = 7                          # MUST be a speaker seen in training
spk_embed = speaker_embed_table[speaker_id]
# spk_embed: (192,)                    learned vector for this speaker
#   Not extracted from audio — looked up from a fixed table
# ── Step 1: Text Encoder ──────────────────────────────────
# Transformer encoder, conditioned on speaker embedding.
# Outputs TWO things per phoneme: a mean μ and std σ (Gaussian parameters).

h_text = text_encoder(phoneme_ids, spk_embed)
# h_text: (1, 192, 20)                one 192-dim vector per phoneme

mu_text    = proj_mu(h_text)            # (1, 192, 20)   mean
sigma_text = proj_sigma(h_text)         # (1, 192, 20)   log-variance

# These define a Gaussian distribution FOR EACH PHONEME:
#   "phoneme #3 should sound like N(μ₃, σ₃) in latent space"
# ── Step 2: Duration Predictor ────────────────────────────
# Predicts how many mel frames each phoneme occupies.
# Uses a flow-based stochastic predictor (not deterministic —
# same text can produce slightly different rhythms each time).

durations = duration_predictor(h_text, noise=randn(...))
# durations: (1, 20)                  e.g. [4, 8, 12, 6, 3, ...]
#   phoneme "HH" → 4 frames, "AH" → 8 frames, etc.

total_frames = sum(durations)           # e.g. 172 frames ≈ 2.0 seconds
# ── Step 3: Expand + Normalizing Flow ─────────────────────
# Repeat each phoneme's (μ, σ) for its predicted duration.

mu_expanded = repeat_by_durations(mu_text, durations)
# mu_expanded: (1, 192, 172)           20 phonemes expanded to 172 frames
#   e.g. phoneme "AH" with μ=[0.3,...] and duration=8 → 8 copies of [0.3,...]

sigma_expanded = repeat_by_durations(sigma_text, durations)
# sigma_expanded: (1, 192, 172)

# Sample from the text-predicted Gaussian
z_text = mu_expanded + sigma_expanded * randn(1, 192, 172)
# z_text: (1, 192, 172)               "what the text encoder thinks speech should be"

# Normalizing flow TRANSFORMS this simple Gaussian sample
# into a realistic speech latent (closer to real speech distribution).
# This is an INVERSE flow: simple → complex, in ONE pass (no iteration).
z = inverse_flow(z_text)
# z: (1, 192, 172)                    same shape, but richer distribution
#   Now z lives in "real speech space" instead of "simple Gaussian space"
# ── Step 4: Decoder — latent → waveform (built-in vocoder)
# The decoder IS a HiFi-GAN — transposed convolutions that
# upsample from frame-rate to sample-rate.

waveform = decoder(z)
# Upsampling: 172 frames × 256 (hop) = 44,032 samples
# waveform: (1, 1, 44032)
#   = 44,032 ÷ 22,050 Hz ≈ 2.0 seconds of audio

# That's it. No vocoder call. No ODE steps. No AR loop.
# One forward pass through the decoder.
# ── Why VITS is fast ──────────────────────────────────────
# Text encoder:      1 forward pass        ~2ms
# Duration predictor: 1 forward pass       ~1ms
# Normalizing flow:  1 forward pass        ~3ms  (no iteration!)
# Decoder:           1 forward pass        ~20ms
# ─────────────────────────────────────────
# Total:             ~26ms for 2s of audio
#
# Compare:
#   VALL-E:  150 AR steps + 7 NAR passes + decode ≈ 1.5s
#   F5-TTS:  32 ODE steps + vocoder                ≈ 500ms
#   VITS:    4 forward passes total                 ≈ 30ms
#
# Tradeoff: no zero-shot voice cloning.
#   New speaker = retrain or fine-tune the whole model.
#   VALL-E/F5-TTS just need a 3-second reference clip.

Hybrid (the 2026 trend)

AR for prosody structure + flow-matching for acoustic quality

Text (string) → G2P tokenizer → phoneme IDs (integers) → Text encoder (Transformer) → contextual vectors (one per phoneme) → AR Transformer (like GPT) → coarse semantic tokens (integers capturing rhythm, intonation, phoneme identity — "what to say and how") → Flow-matching generator → mel spectrogram (fine-grained acoustic detail — "exactly how it sounds") → Vocoder → raw waveform

Two stages, each doing what it's best at. Stage 1: an autoregressive Transformer generates coarse semantic tokens that capture the high-level structure — which phonemes, how long, what rhythm and intonation. Stage 2: a flow-matching model takes those tokens (plus a speaker embedding from a reference clip) and generates the fine acoustic detail. Think of stage 1 as writing the sheet music and stage 2 as performing it with a specific voice.

ModelKey detail
CosyVoice (Alibaba)AR LM for semantic tokens + flow-matching for acoustic generation.
VALL-E 2AR + NAR stages with flow-matching refinement.

Pros: Best of both — natural prosody from AR + high quality from flow-matching.

Cons: Complex multi-component pipeline, more moving parts to optimize.

Typical latency: ~300ms-1s (AR bottleneck + flow refinement).

CosyVoice Inference: Step-by-step Pseudocode

Generating 2 seconds of speech from "Hello world", cloning a 3-second reference voice. Concrete tensor shapes at every step.

Key rates

sample_rate       = 24,000 Hz     # output audio
mel_frame_rate    = 50 Hz         # mel spectrogram frames per second
token_rate        = 25 Hz         # speech tokens per second
mel_bins          = 80            # frequency resolution
codebook_size     = 6,561         # FSQ codebook (CosyVoice 2)

# So: 1 speech token = 2 mel frames = 960 audio samples = 40ms

Step 0: Frontend — prepare inputs (no neural networks)

# ── What you want the model to say ────────────────────────

text = "Hello world, this is a test."

text_tokens = g2p_tokenizer(text)       # rule-based, NOT neural
# text_tokens: (1, 8)                   int IDs, e.g. [9707, 1879, 11, ...]
#   each integer = one BPE subword


# ── The voice you want to clone (3-second reference clip) ─

ref_audio = load("reference.wav")       # (72000,) raw samples at 24kHz

prompt_speech_tokens = s3_tokenizer(ref_audio)   # separate ONNX model
# prompt_speech_tokens: (1, 75)         int IDs, 3s × 25 tokens/s = 75
#   each integer ∈ [0, 6561) represents 40ms of speech content

prompt_mel = mel_spectrogram(ref_audio)
# prompt_mel: (1, 80, 150)              float, 3s × 50 frames/s = 150

spk_embedding = campplus(ref_audio)     # speaker verification network
# spk_embedding: (1, 192)              float, L2-normalized
#   ONE vector capturing "who this person is"

Stage 1: LLM — text → speech tokens (autoregressive, slow)

# The LLM is Qwen2.5-0.5B — same family as a chat model!
# It has TWO embedding tables: one for text, one for speech tokens.

text_embeds   = text_embed_table(text_tokens)          # (1, 8, 896)
prompt_embeds = speech_embed_table(prompt_speech_tokens) # (1, 75, 896)

# Concatenate into one input sequence, just like a GPT prompt:
lm_input = concat([
    sos_embed,        # (1, 1, 896)    start-of-sequence
    text_embeds,      # (1, 8, 896)    "what to say"
    task_embed,       # (1, 1, 896)    "this is a zero-shot TTS task"
    prompt_embeds,    # (1, 75, 896)   "sound like this person"
])
# lm_input: (1, 85, 896)

# Autoregressive loop — generate speech tokens ONE AT A TIME
generated_tokens = []
for step in range(50):                  # 2s × 25 tokens/s = 50 tokens
    hidden = qwen2(lm_input, kv_cache)  # (1, 1, 896)
    logits = linear_head(hidden)        # (1, 6564)  →  6561 codes + 3 special
    token  = sample(logits)             # scalar int
    generated_tokens.append(token)

# Output: (1, 50) int — 50 speech tokens = 2 seconds of speech
# These encode WHAT to say + rhythm + intonation
# But they are NOT audio yet — just integers!

Stage 2: Flow matching — speech tokens → mel spectrogram (iterative, 10 steps)

# Step 2a: Encode tokens into conditioning signal μ
all_tokens = concat([prompt_speech_tokens, generated_tokens])
# all_tokens: (1, 125)                 75 prompt + 50 generated

mu = token_encoder(all_tokens)          # small Transformer, NOT the LLM
# mu: (1, 80, 250)                     125 tokens × 2 (upsample to mel rate)
#   This is the "GPS directions" — tells flow matching what to generate


# Step 2b: Set up masked mel
masked_mel = concat([
    prompt_mel,                         # (1, 80, 150)  ← real reference mel
    zeros(1, 80, 100),                  # (1, 80, 100)  ← to be filled in
], dim=time)
# masked_mel: (1, 80, 250)


# Step 2c: ODE solver — iteratively denoise
x = randn(1, 80, 100)                  # start from pure Gaussian noise

for step in range(10):                  # 10 ODE steps
    t = step / 10                       # time: 0.0 → 1.0

    # U-Net sees: current noisy mel + conditioning + speaker + timestep
    unet_input = concat([x, mu_gen_region], dim=channels)
    # unet_input: (1, 160, 100)         80 (noisy mel) + 80 (conditioning)

    velocity = unet(unet_input, spk_embedding, t)
    # velocity: (1, 80, 100)            direction to move x

    x = x + (1/10) * velocity           # Euler step

# Output: (1, 80, 100)  float — mel spectrogram for 2s of speech
# 80 frequency bins × 100 time frames
# This is a "heat map" of how the audio sounds

Stage 3: Vocoder — mel → waveform (single forward pass, fast)

mel = x                                # (1, 80, 100) from flow matching

f0 = f0_predictor(mel)                 # pitch contour
excitation = harmonic_source(f0)        # sine waves at predicted pitch

waveform = hifigan_decoder(mel, excitation)
# waveform: (1, 48000)                 100 frames × 480 samples/frame
#   = 48,000 samples ÷ 24,000 Hz = 2.0 seconds of audio

save("output.wav", waveform, sr=24000)  # done!

Real-time TTS for Games

Why games care differently about TTS

Human conversational reaction time is ~200ms. If an NPC takes >500ms to respond, it feels robotic and breaks immersion. The target for interactive game dialogue is:

Time-to-first-audio: 150–300 ms

Why most SOTA TTS fails for games

ArchitectureProblemTypical latency
Diffusion TTS (20-50 steps)Must denoise full spectrogram before any audio plays>1s
AR codec LM (VALL-E)Sequential token generation: 3s speech = ~150 tokens generated one by one~500ms-2s
Classical TTS (Tacotron)Generates full mel before vocoder runs~1-2s

All of these generate the complete utterance before playback starts. Games need the opposite.

What games need: streaming TTS

Text stream → Incremental TTS → Audio stream (play while still generating)

Like this:

Player: "Where is the sword?"
NPC response timeline:
  0ms    → LLM starts generating text tokens
  80ms   → first text tokens arrive at TTS
  150ms  → first audio chunk plays: "It's..."
  200ms  → next chunk plays: "in the..."
  300ms  → "...cave to the north"
  (all three stages overlapping, not sequential)

The prosody look-ahead tradeoff

This is the hard problem most ML people miss. Prosody (intonation, emphasis, pacing) depends on future context:

"I never said he stole the money"
       ^--- emphasis on different words completely changes meaning

Streaming TTS doesn't know future words yet.
So: latency ↔ prosody quality is a fundamental tradeoff.

Lower latency = less context for prosody decisions = less natural speech. This is why single-pass models (VITS) sound flat — they commit to prosody immediately without look-ahead.

The full pipeline latency breakdown

In a game speech agent (ASR → LLM → TTS), the bottleneck is often not TTS:

Key insight: the system must be designed for pipeline parallelism — ASR streams partial transcripts to LLM, LLM streams tokens to TTS, TTS streams audio to the player. No stage waits for the previous one to finish.

Interview answer: real-time TTS for games

"The main challenge is latency. Traditional TTS generates the full acoustic representation before synthesis, which introduces hundreds of milliseconds of delay. In interactive settings like games, we need streaming generation where speech starts playing within ~200ms. That requires architectures that support incremental synthesis — streaming vocoder, chunk-based generation — while still maintaining natural prosody, which is fundamentally hard because prosody depends on future context. The practical solution is a combination of pipeline parallelism across ASR/LLM/TTS, short utterance generation, pre-generated common lines, and choosing the right model for each use case: single-pass for speed, flow-matching for quality, pre-recorded for critical dialogue."

The Key Insight: Semantic / Acoustic Hierarchy

The field has converged on a two-level hierarchy that separates what to say from how it sounds:

Semantic layer  →  "prosody, rhythm, phoneme timing"   (coarse, high-level)
    ↓
Acoustic layer  →  "timbre, texture, waveform detail"   (fine, low-level)
SystemSemantic layerAcoustic layer

This hierarchy is why hybrid systems work: the semantic layer handles the hard part (prosody depends on meaning), and the acoustic layer handles the easy-but-detailed part (making it sound like a real person). Separating them lets each stage use the best tool for the job.

Interview Answer (30 seconds)

"Modern TTS has three main paradigms. First, autoregressive codec LMs like VALL-E treat speech as discrete audio tokens and generate them with a transformer. They produce very natural prosody and enable strong voice cloning, but inference is slow because tokens are generated sequentially. Second, diffusion or flow-matching models like VoiceBox or F5-TTS generate acoustic features such as mel spectrograms by denoising noise conditioned on text and speaker embeddings. They achieve the highest quality but require multiple denoising steps. Third, feed-forward models like VITS generate speech in a single pass with an integrated vocoder. They are extremely fast but less flexible for zero-shot voice cloning. The trend in 2025-2026 is hybrid systems that use a language model to generate coarse semantic speech tokens and a diffusion or flow model to synthesize the final acoustics."

The single most important sentence: "Modern TTS separates semantic speech structure (prosody, rhythm, phoneme timing) from acoustic realization (timbre and waveform), typically using a language model for the former and diffusion or codec decoding for the latter."
