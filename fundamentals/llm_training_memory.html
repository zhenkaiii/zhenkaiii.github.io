LLM Training: GPU Memory Math & Parallelism

Distributed Training Systems

The One Rule

BF16 training: ~16 bytes per parameter. FP8 training: ~13 bytes per parameter.
Adam optimizer states (8 bytes) dominate and are non-negotiable.

What Goes on the GPU

Fixed cost (doesn't change with batch/seq)

ComponentBF16FP8Why
Weights2B1BThe model parameters
Gradients2B2BGrad accumulation needs FP16 precision
Adam m (1st moment)4B4BRunning mean of gradients, must be FP32
Adam v (2nd moment)4B4BRunning variance of gradients, must be FP32
Fixed total12B/param11B/param

Why Adam must be FP32: m and v accumulate tiny gradient updates over thousands of steps. In FP16, small updates round to zero and training stalls or diverges. (8-bit Adam from bitsandbytes brings this to 1+1=2B, but FP32 is the safe default.)

Variable cost (scales with batch × seq)

Activations are stored during the forward pass so the backward pass can compute gradients. They have nothing to do with parameter count — they scale with batch size, sequence length, hidden dim, and layer count.

Activation per layer ≈ 12 × batch × seq_len × hidden_dim × bytes_per_element

For 8B model (32 layers, hidden=4096), BF16:
  Per layer ≈ 12 × batch × 4096 × 4096 × 2 bytes

Interview framing: "Weights, gradients, and optimizer states are fixed cost — about 12 bytes per parameter regardless of batch size. Activations are variable cost — they scale linearly with batch size and sequence length. That's why long-context training is expensive."

Gradient Checkpointing

Trade compute for memory: don't store activations during forward pass, recompute them during backward.

Activation memoryCompute cost
No checkpointing~100 GB (mbs=8, seq=4K)1x
Gradient checkpointing~10-15 GB~1.3x

Cuts activation memory by ~6-8x at a ~30% compute overhead. Almost always worth it for large models.

Napkin Math: 8B Model

Fixed cost:  12 bytes × 8B params = 96 GB
Activations: mbs=8, seq=4K        ≈ 100 GB (without checkpointing)
                                   ≈ 15 GB  (with checkpointing)

Without checkpointing:  96 + 100 = 196 GB → 3 H100s minimum
With checkpointing:     96 + 15  = 111 GB → 2 H100s minimum

Add the "~4 bytes/param" activation ballpark and you get the ~16 bytes/param rule of thumb. But remember: that 4 assumes a specific batch/seq config. Double the batch, double the activations.

Parallelism Decision Tree

Start from the innermost and work outward:

Step 1: Does the model FIT on one GPU? │ Yes ──→ Data Parallelism (DP) only. Done. No ──→ Step 2. Step 2: Tensor Parallelism (TP) within one node. Shard weights across GPUs on NVLink. TP = 2, 4, or 8 (stay within one node). │ Fits now? ──→ Add DP across nodes for throughput. Done. Still no? ──→ Step 3. Step 3: Pipeline Parallelism (PP) across nodes. Split layers across nodes. │ Combine: TP (intra-node) + PP (inter-node) + DP (replicas).

The rule: chattiest parallelism gets the fastest interconnect.
TP communicates every layer → needs NVLink (intra-node).
PP communicates between stages → tolerates inter-node.
DP communicates once per step → goes on the outermost ring.

Fitting vs. Throughput

TP and PP solve the fitting problem. DP solves the throughput problem.
Once the model fits, every additional DP replica doubles throughput linearly.

Double the DP nodes → double the global batch size (GBS) → double the throughput.

DP scaling is near-linear but not perfect:

DP replicasScaling efficiency
4~95%
16~90%
64~80-85%
256Starts degrading (communication dominates)

For typical runs (4-32 replicas), "double nodes = double throughput" holds.

The Interview Answer (30 seconds)

"Full-precision BF16 training costs roughly 16 bytes per parameter — 2 for weights, 2 for gradients, 8 for Adam optimizer states, and ~4 for activations depending on batch and sequence length. An 8B model needs ~96 GB just for the fixed cost, so it doesn't fit on one H100. I'd use TP=2 within a node to fit, then data parallelism across remaining GPUs for throughput. Double the DP replicas, roughly double the throughput."

If they push on parallelism:

"The rule is: chattiest parallelism gets the fastest interconnect. TP communicates every layer, so it stays within a node on NVLink. PP communicates between stages, tolerates inter-node. DP communicates once per step, goes on the outermost ring. For 70B+ you need all three."

Attention Compute vs. KV Cache

Training: attention compute is O(seq²) per layer — every token attends to all previous tokens. No shortcut.
Inference: each new token computes attention against the cached KV pairs — O(seq) per token, but the KV cache memory grows linearly with context length and is the main bottleneck.

KV cache per layer = 2 × seq_len × head_dim × num_kv_heads × bytes
Full model         = above × num_layers

Example: Llama 3 70B, seq=8K, BF16, 80 layers, 8 KV heads, head_dim=128
  Per layer: 2 × 8192 × 128 × 8 × 2 = 32 MB
  Full model: 32 MB × 80 = 2.5 GB  (per sequence!)
  Batch of 32: 80 GB — an entire H100.

For long context (128K+) and deep models, KV cache dominates inference memory. Every technique below exists to compress it — but must be baked in at training so accuracy is preserved.

KV Cache Compression: Attention Variants

MethodKV headsKV cache size vs MHAOrigin
MHA (Multi-Head)= Q heads (e.g. 64)1x (baseline)Vaswani 2017

GQA — the current default

Multiple Q heads share one KV head. Llama 3 70B uses 64 Q heads with 8 KV heads → 8x KV cache reduction. Negligible quality loss, huge inference win. This is what everyone ships.

MLA — DeepSeek's approach

Instead of storing separate K and V per head, compress them into a single low-rank latent vector per token. At attention time, project the latent back out to K and V.

Standard: cache K (d_head × n_kv_heads) + V (d_head × n_kv_heads) per token per layer
MLA:      cache one latent vector (d_latent) per token per layer
          where d_latent << d_head × n_kv_heads

Compression comes from: d_latent is much smaller than the full KV.
Even better ratio than GQA for deep models.

Tradeoff: extra projection ops at inference, but memory saving dominates for long-context / large-batch serving.

Sliding Window Attention (Mistral / Gemma 2)

Each layer only attends to the last W tokens (e.g. W=4096) instead of the full context. KV cache is bounded: only need to store W entries per layer, regardless of total sequence length.

Key insight: training compute is still O(seq²) for full-attention layers. Sliding window doesn't save training FLOPs much — the win is inference KV cache is bounded to the window size.

QK Norm & Hybrid Attention

QK Norm

Apply RMSNorm to Q and K vectors before the dot product in attention.

Problem: Pre-softmax logits = QKT / √d. The norms of Q and K can grow unboundedly during training (residual stream accumulates magnitude). When logits get huge → softmax saturates to one-hot → gradients vanish → "attention entropy collapse".
Fix: RMSNorm on Q and K bounds their norms → logits stay controlled → stable training. Used in Gemma 2, ViT-22B, Cohere Command R.

Hybrid Attention (Sliding Window + Full)

Alternate between sliding-window layers and full-attention layers (e.g. Gemma 2: 5 sliding : 1 full).

TrainingInference
ComputeSliding layers slightly cheaper, minor speedupNot the main point
KV cacheN/ASliding layers: bounded cache. Full layers: full cache. Big net saving.
QualityFull-attention layers propagate long-range info into residual streamPreserved

Bottom line: Hybrid attention is an inference optimization. You accept the training cost (slightly less accuracy pressure from fewer full-attention layers) to get dramatically smaller KV caches at serving time. Training time difference is minimal — it's about what you bake into the architecture for deployment.
